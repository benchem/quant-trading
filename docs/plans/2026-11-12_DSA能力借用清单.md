# DSA → quant-trading 能力借用清单

> 日期：2026-11-12 ｜ 性质：**只读分析报告，本任务未修改任何代码**
> 源：DSA（`/root/projects/dsa`，MIT，`daily_stock_analysis`）
> 目标：`/root/workspaces/quant-trading`（LLM 在 `analyzer/agent/llm.py`，手写 http server `analyzer/server.py`，单页 `analyzer/web/app.js`，数据面 `analyzer/datastore.py`）

---

## 0. 一句话结论

DSA 值得借的不是它的体量（FastAPI + React + LiteLLM + 多 Agent 编排，我们的工程装不下也不需要），而是它把 LLM 输出**约束成结构化决策资产**的那套纪律：统一评分口径、报告后结构化抽取、token 成本台账、缓存友好 Prompt、多渠道推送隔离、工具层与数据层解耦。其中 **8 项能直接落成我们现有 4 个痛点**（AI 报告不可统计、token 成本黑箱、单股上下文 19k tokens 慢、站内信是唯一通知面），另外 6 项明确判定**不要搬**（框架级依赖，收益/成本严重倒挂）。

## 2. 值得借清单（按优先级 P0→P2）

### P0-1 统一评分/动作口径（decision scale）→ 让 AI 报告可统计、可回测

- **DSA 出处**：`src/schemas/decision_scale.py:1-46`
  五档 `DecisionScaleBand(min,max,signal_key,action,decision_type,label_zh,description_zh)`：80-100 强烈买入 / 60-79 买入 / 40-59 观望 / 20-39 减仓 / 0-19 卖出；三态 `decision_type(buy|hold|sell)` 保留给统计，八态 `action` 表达细粒度；并给出 `CANONICAL_DECISION_SCALE_PROMPT_ZH`——把同一口径**原样注入 prompt**，另有「score≥60 但 action=watch 必须写降级原因」的冲突护栏（`score_action_conflicts_without_guardrail`）。
- **我们的现状缺口**：`analyzer/agent/prompts.py` `SYSTEM_PROMPT`（第 21 行起）要求模型自由给结论；`analysis.py` 落盘的 `report` 是纯 Markdown，无法与 `stock_analysis/plugins/` 的量化信号、`datastore.positions()` 的持仓、`backtest.py` 的回测做任何 join。
- **怎么接**：
  1. `prompts.py` 的 `SYSTEM_PROMPT` 末尾追加一段口径（照抄 `CANONICAL_DECISION_SCALE_PROMPT_ZH` 的语义，档位数值可直接沿用），并在 `USER_TEMPLATE` 要求报告尾部输出固定 `## 决策摘要` JSON 代码块。
  2. `analysis.py` 的 `generate()` 里在写缓存前解析该块（解析失败 → `warnings` 追加"决策摘要缺失"，报告仍照常返回，不做 fail-fast）。
  3. `data/ai/{code}.json` 增字段 `decision: {score, action, decision_type, guardrail_reason}`；前端 `renderAI()`（app.js:3531）meta 行加彩色动作徽标，与 `renderTradeMarkers()`（app.js:1479）叠加显示"AI 当时怎么说"。
  4. `bump PROMPT_VERSION v4→v5` 触发指纹失效、报告重生成（`analysis.py:_fingerprint` 已含 prompt 版本语义）。
- **工作量**：小（prompt 段 + 一个 20 行解析函数 + 前端徽标 + 1 个测试）。
- **风险**：解析脆弱 → 用"缺块不报错只告警"；老缓存不自动失效（靠 `PROMPT_VERSION`）。
- **不借什么**：不引入 pydantic、不搬 `decision_profile.py`/`decision_action.py` 的 8 态全量枚举与 backfill 溯源（我们是单用户自用工具，`legacy_unknown` 这类历史包袱无需）。

### P0-2 报告→结构化信号抽取（report → signal → 可查询资产）

- **DSA 出处**：`src/services/decision_signal_extractor.py:1-60`（`build_decision_signal_payload_from_report`，含 `_CONFIDENCE_MAP` 高/中/低→0.8/0.6/0.4）、`src/services/decision_signal_service.py`（落库+查询）、`apps/dsa-web/src/types/decisionSignals.ts`（前端契约）、`src/utils/sniper_points.py:73 extract_sniper_points`（买卖点位鲁棒解析：中文数字/区间/None 容错）。
- **我们的现状缺口**：日记面 `analyzer/journal.py` + `GET /api/journal`（server.py:518）只有人工笔记与规则事件；AI 结论没有沉淀成"某天某股模型说了什么"的时间序列，因此无法回答"AI 看多的股票后来涨没涨"。
- **怎么接**：新增 `analyzer/agent/signals.py`（纯函数，无新依赖）：从 P0-1 的 `decision` 块 + `sniper_points` 式点位解析，追加写 `data/users/{user}/ai_signals.jsonl`；`server.py` do_GET 链加 `elif path == "/api/ai_signals"`（复用现有 params/user 解析写法）；`app.js` 在「交易记录」或「日记」tab 内加一条 AI 观点时间线（不做新 tab，遵守现有单页结构）。有了这张表，`backtest.py` 就能把"AI 信号 vs 后续收益"当策略验证。
- **工作量**：中（≈ 150 行 Python + 60 行 JS + 测试）。
- **风险**：JSONL 无 schema 演进 → 每行带 `schema_version` 与 `prompt_version`；与既有 `positions()` 口径冲突 → 信号只读不写持仓。
- **不借什么**：不搬 `DecisionSignalService` 的 DB 仓储层与 `skill_opinion_weight/sample_service`（样本加权/胜率统计需要长期数据积累，我们现在没有）。

### P0-3 token 用量归一 + 成本台账（网关共享，429 真实存在）

- **DSA 出处**：`src/llm/usage.py`（40KB：`provider_usage_v1` schema、usage 归一与截断到 `MAX_SIZE_BYTES=4096`、prompt 消息 HMAC 指纹便于跨请求去重/审计）、`src/llm/provider_cache.py:85,586`（`PromptCacheTelemetryFilteredUsage` / `filter_prompt_cache_telemetry`，缓存命中 token 单独归类）、`src/llm/generation_params.py`（按 provider 能力过滤 temperature/max_tokens 等）。
- **我们的现状缺口**：`llm.py:86` 已经把 `usage` 原样返回，`analysis.py:91`、`brief.py:184`、`review.py:53` 也都存了；但前端只在 `ai-meta` 显示 `total_tokens`（app.js:3535），**没有任何跨天累计、没有按消费方（个股分析/美股简报/LLM 复盘）归因**。而 `jobs.py` 文档明写：单次 ≈19k tokens、≈6.5 分钟、三类消费共用同一 `AI_BASE_URL` 网关，网关确有限流。
- **怎么接**：
  1. `llm.py` 内加一个 10 行 `normalize_usage(raw)`：缺键补 0、`prompt/completion/total` 三键归一、剔除网关返回的超长杂项（DSA 的 4096 字节截断思路），**保持 `{content, usage}` 返回契约不变**。
  2. 新增 `analyzer/agent/usage_ledger.py`：按 `(day, consumer, model)` 累计 tokens 与估算成本，落 `data/ai_usage.jsonl`；调用方只需 `record(consumer="analysis", usage=resp["usage"])`。
  3. `server.py` 加 `GET /api/ai_usage`（返回近 N 天汇总）；前端在「站内信」侧栏或 `renderUpdateChip`（app.js:4308）附近加一个成本 chip。
  4. `jobs.py` 的 `max_workers` 决策有了数据依据（是否该降到 1 或按时段错峰）。
- **工作量**：小-中。
- **风险**：成本单价写死 → 走 env（`AI_PRICE_IN/OUT`），未配置时只显示 token 不显示金额（符合 DSA "不写死模型名/额度" 的护栏精神）。
- **不借什么**：**不搬 HMAC 遥测**（DSA 用它是为了满足上游 provider 审计与合规去重，我们的台账只是自用记账，加 HMAC 纯属负担）；不引入 LiteLLM。

### P1-4 Prompt 缓存友好布局（单次 19k tokens、每次重跑全额计费的直接解药）

- **DSA 出处**：`src/llm/provider_cache.py:117-230 ProviderCacheCaps`（按 provider family 判定支持哪些缓存能力）、`509 apply_prompt_cache_hints`（把稳定前缀标记为可缓存，Anthropic 走 `system` + `cache_control`，`:617`）、`447 infer_provider_family`。
- **我们的现状缺口**：`analyzer/agent/context.py` 的 `build_prompt()` 把「SYSTEM_PROMPT（稳定）+ USER_TEMPLATE（含行情/新闻/插件输出，高度易变）」直接拼；`analysis.py:_fingerprint(context, model)` 一变就全量重跑；每天 08:00 简报 + 盘后复盘 + 个股分析重复发送同一套长系统 prompt。
- **怎么接**（不新增依赖，纯工程约束）：
  1. `context.py` 重排 message 数组：`[system: 角色+口径+工具说明（完全静态）]` → `[user: 变化数据]`，**把任何日期/价格相关的词从 system 段彻底移出**（这是 DeepSeek/网关隐式前缀缓存生效的唯一前提）。
  2. 若网关是 DeepSeek 系（`AI_BASE_URL` 指向 one-api，模型名可判定），沿用 DSA 的"按 family 决定能力"思路：只有识别到支持显式 `prompt_cache_key` 的后端才注入该字段，其余静默跳过（照 DSA 的 best-effort 语义，异常不影响主链路）。
  3. 把 P0-3 的 usage 归一里读 `prompt_cache_hit_tokens / cached_tokens`（DeepSeek 系返回字段），前端 meta 显示"缓存命中 x%"，让收益可观测。
- **工作量**：小（重排 prompt + 一个 family 判定 + 一个可选字段）。
- **风险**：one-api 网关是否透传缓存字段未知 → **上线前先 dry-run 一条对照 usage 字段**，命中为 0 也不损失什么（纯布局改善）。

### P1-5 错误分级 + retryable 语义（429 与参数错误的处理不能混为一谈）

- **DSA 出处**：`src/llm/errors.py:125-150`（`call_litellm_once`：只对"生成参数被拒"这一类错误做**一次**带恢复的重试，其余不盲重试）、`generation_backend.py:71`（`retryable: bool` 是错误对象的一等属性）。
- **我们的现状缺口**：`llm.py:68-78` 已把 401/403/429/4xx/5xx 映射成中文 `AIError(status)`，这点比 DSA 文档化得更好；但 `jobs.py` 消费时无法区分"重试有意义"（429/超时）与"重试没意义"（401/参数错），目前只能整任务 failed。
- **怎么接**：`AIError` 增 `retryable: bool` 字段（Timeout/429/5xx=True，401/403/格式异常=False）；`jobs.py` 仅对 retryable 做 1 次退避重试（如 30s），并在任务状态里回传 `retryable`，前端 `renderAIFor`/提示区据此区分文案（"稍后自动重试" vs "请检查配置"）。
- **工作量**：小。
- **风险**：退避重试占用 `max_workers=2` 的槽位 → 重试放在同一次 worker 内且总耗时受 `AI_TIMEOUT` 约束；重试次数硬编码为 1，不引入退避库。

### P1-6 通知渠道抽象 + 单渠道失败隔离

- **DSA 出处**：`src/notification_sender/wechat_sender.py:1-25`（统一 send 入口、`chunk_content_by_max_bytes` 按字节分片（`src/formatters.py:618`）、`WECHAT_IMAGE_MAX_BYTES=2MB` 上限保护）、`AGENTS.md:219`「单一通知渠道失败不应拖垮整个分析主流程」；15 个 sender 同构。
- **我们的现状缺口**：`NotificationHub`（notify.py）做得已经不错（多用户、按自选股路由、归属查不到退化广播），但出口只有站内信 + `mailer.py`；且推送与主流程的失败隔离契约是**隐式**的。
- **怎么接**：
  1. `notifybox.core` 的 push 出口后面定义 `class Channel: def send(text, level, meta) -> bool`（一个协议 + 一个 try/except 循环），先落地 `Inbox`、`Email` 两个实现，为将来加企业微信/飞书/TG 留位（可直接抄 DSA 对应 sender 的 webhook 逻辑，几十行一个）。
  2. 借 `chunk_content_by_max_bytes`：Markdown 报告按渠道字节上限分片，避免邮件/推送截断（DSA 用 4096 字节系上限）。
  3. 把"渠道失败不阻塞主流程"写进 `tests/test_inbox.py` 断言 + AGENTS 式约束说明。
- **工作量**：小（协议 + 2 实现 + 分片函数）。
- **风险**：多渠道重复推送 → `push(dedup=True)` 已有，扩展时按 `(day, key, channel)` 去重。

### P1-7 Agent 工具层 = datastore 薄封装（为将来"问股"铺路）

- **DSA 出处**：`src/agent/tools/registry.py`（`ToolParameter/ToolDefinition` + `@tool` + 多 provider schema 生成）、`tools/market_tools.py / data_tools.py / search_tools.py`（**全部是对 data provider 的薄封装，不含业务逻辑**）、`src/agent/strategies/{router,aggregator,strategy_agent}.py`（15 策略 → 并行出观点 → 聚合，`protocols.py:216 AgentOpinion/260 StrategyOpinion/281 StrategyConflict` 定义置信度、信号归一、冲突记录）。
- **我们的现状缺口**：`context.py:AI_INPUT_MODELS` 是**手工静态清单**（注释："新增插件需手动加入才会纳入 AI 上下文"）——模型越加越多，喂给 LLM 的东西靠人脑维护，这正是 DSA 用 registry 解决的问题。
- **怎么接**（**不引入 function-calling**，我们的网关单次调用已 6.5 分钟，多轮工具循环会失控）：
  1. `stock_analysis/plugins/` 每个插件声明 `TOOL_SPEC = {name, description, params}`，`context.py` 由声明自动生成输入清单，去掉手工表（等价于 DSA registry 的收益，零新依赖）。
  2. 若将来做问股，走 DSA 的**单次结构化多观点**形态（`strategies/` 一次调用产出 N 个 `AgentOpinion` 再 `aggregator` 聚合 + 记录 `StrategyConflict`），而不是 `orchestrator.py`（93KB）那套多轮 ReAct。
- **工作量**：小（声明化）；中（多观点聚合，可后置）。
- **风险**：spec 漂移 → 加 `tests/test_plugins.py` 断言"每个插件必须有 TOOL_SPEC 且字段齐全"（对齐现有 `tests/test_architecture.py` 的架构契约风格）。

### P2-8 分层与验证矩阵的工程纪律（不借代码，借规则）

- **DSA 出处**：`AGENTS.md:9-30`（目录边界硬规则、"不写死密钥/模型名/端口/环境差异逻辑"、"新增配置项必须同步 `.env.example` 与文档"、"优先复用现有模块，不新增平行实现"）、`:146-196` 验证矩阵（改动面→命令映射）、`:203-224` 稳定性护栏（"单一数据源失败不应拖垮整个流程"、"改 API/Schema/报告载荷要同时检查前后端兼容"）。
- **我们的现状**：`analyzer/` 与 `stock_analysis/` 边界其实比 DSA 更清晰，`tests/test_architecture.py` 已在做依赖约束（brief.py:18 注释即引用它），是**我们的优势**，不要为了对齐 DSA 而放松。
- **怎么接**：把上述四条硬规则补进本仓库的 AI 协作约束（根 `AGENTS.md` 若无则新建一份短的），并把"改动面→验证命令"做成表——因为我们即将开始动 `llm.py`/`prompts.py`/`server.py`/`app.js` 这四个高联动面。
- **工作量**：小。
- **风险**：规则过多没人遵守 → 只补与本次借用直接相关的 4-6 条。

## 3. 明确「不要借」清单（判定与理由，防止后续任务误搬）

| # | DSA 资产 | 为什么不要 |
|---|---|---|
| N1 | `src/llm/local_cli_backend.py`（**103KB**）、`backend_factory.py`、多后端路由、LiteLLM 依赖 | 我们单一 OpenAI 兼容网关，86 行足够。引入 = 新增重依赖 + 千行未用代码，纯负债 |

| N3 | `apps/dsa-web/`（React+TS+stores+hooks+e2e） | 我们 `app.js` 已 4807 行且无构建链。引入 React = 引入 node 构建、双份心智模型，运维成本远超收益。只借它的**类型契约意识**（`src/types/*.ts` 那种"字段集中定义"）：在 `app.js` 顶部集中声明 `decision` 块字段名即可 |

## 5. 硬约束与风险汇总

1. **不改返回契约**：`chat_completion` 仍返回 `{content, usage}`；`/api/ai_analysis` 的 200/202 + `poll_ms` 语义（jobs.py:8-14）不动，前端 `AI_POLL_MS/AI_POLL_MAX_FAILS`（app.js:3552）逻辑复用。
2. **不新增第三方依赖**：`requirements.txt` 现只有 pandas/pyarrow/tqdm/requests/baostock/akshare(+可选 TLS/matplotlib)。本清单 8 项全部可用标准库实现（这是刻意选的——DSA 很多设计是 pydantic/litellm 加持下的，我们只取其**语义**）。
3. **不引入前端构建链**：所有前端改动继续写在 `analyzer/web/app.js`，沿用 `$(...)`/`escHtml`/`mdToHtml` 既有工具函数。
4. **成本护栏**：任何 prompt 改动都可能触发全量报告重生成 → 逐个 code 手动 `refresh` 验证，不要一次性清空 `data/ai/`（单次 6.5 分钟 × N 只会打满共享网关并真实扣费）。
5. **口径唯一性**：`decision` 分档一旦写入 `ai_signals.jsonl` 就是历史数据，改分档必须同时改 `schema_version`，否则后续统计口径断裂（DSA 用 `CANONICAL_DECISION_SCALE_VERSION = "decision-scale-v1"` 正是为此）。
6. **合规**：搬任何具体代码片段前先确认其来源——DSA 根目录 `THIRD_PARTY_NOTICES.md` **当前为空**，不能当作"全仓 MIT"的凭据；MIT 与 Apache-2.0 的 LICENSE 副本与来源标注都必须随片段一起落地（见 §6）。
